# Тема 3. Pydantic (модели данных)

## Введение

В автотестах API мы постоянно имеем дело с JSON-данными: отправляем запросы, получаем ответы, проверяем структуру и значения. Ручная проверка каждого поля через `response.json()["user"]["id"]` — это путь к ошибкам и нечитаемому коду.

**Pydantic** — это библиотека для валидации данных и управления моделями. Она позволяет описать структуру данных в виде Python-классов с аннотациями типов, а затем автоматически проверять, что приходящий JSON соответствует этой структуре. Если данные невалидны — Pydantic выбросит исключение с понятной ошибкой, что сэкономит часы отладки.

Для тестировщика Pydantic даёт:
- **Читаемость** — модель служит документацией API.
- **Безопасность** — вы сразу видите, что поле `age` пришло строкой, а должно быть числом.
- **Удобство** — работаете с объектами, а не с сырыми словарями (работает с автодополнением IDE).

В этой теме мы будем опираться на аннотации типов, изученные ранее, и применим их на практике.

> Официальная документация: https://pydantic.dev/docs/validation/latest/get-started/

## Как установить Pydantic?

Так как это библиотека сторонняя то перед её использованием нужно установить следующей командой:
```
pip install pydantic
```

После установки класс `BaseModel` и другие компоненты `Pydantic` можно импортировать в код проекта.

## Создание модели

Модель — это класс, наследующий от `BaseModel`. Поля описываются как атрибуты класса с аннотацией типа.

Пример простейшей модели пользователя:

```python
from pydantic import BaseModel

class User(BaseModel):
    id: int
    name: str
    email: str
    is_active: bool = True   # значение по умолчанию
```

Теперь мы можем создать экземпляр модели из словаря или напрямую:

```python
# Способ 1. Из словаря
user_data = {"id": 1, "name": "Anna", "email": "anna@example.com"}
user = User(**user_data)   # распаковка словаря / преобразование dict в объект модели
print(user.name)           # Anna

# Способ 2. С явными аргументами
user2 = User(id=2, name="Alex", email="alex@example.com", is_active=False)
```

Важно: Pydantic автоматически приводит типы, если это возможно. Например, если пришло `{"id": "123"}` (строка), он преобразует в `int`. Это удобно, но нужно помнить о возможных неожиданностях.

---

## Валидация

При создании модели Pydantic проверяет все поля. Если данные не соответствуют типам, выбрасывается исключение `ValidationError`.

```python
try:
    invalid = User(id="not_a_number", name="Test", email="test@test.com")
except ValidationError as e:
    print(e.json())   # подробное сообщение об ошибке
```

В тестах мы часто обрабатываем такие ошибки, чтобы явно упасть с понятным сообщением — это лучше, чем ловить `KeyError` или `TypeError` в недрах кода.

## Вложенные модели и списки

Реальные API редко бывают плоскими и Pydantic поддерживает такие вложенности и коллекции.

Допустим, у нас есть заказ, содержащий список товаров:

```python
class Item(BaseModel):
    name: str
    price: float
    quantity: int

class Order(BaseModel):
    order_id: int
    customer: User          # вложенная модель
    items: list[Item]       # список моделей
    total: float
```

Теперь мы можем спарсить сложный JSON одной командой:

```python
raw_json = {
    "order_id": 1001,
    "customer": {"id": 3, "name": "Ivan", "email": "ivan@mail.com"},
    "items": [
        {"name": "Laptop", "price": 999.99, "quantity": 1},
        {"name": "Mouse", "price": 25.50, "quantity": 2}
    ],
    "total": 1050.99
}

order = Order(**raw_json)
print(order.customer.name)        # Ivan
print(order.items[0].price)       # 999.99
```

Обратите внимание: если в `items` окажется поле, которого нет в модели `Item`, Pydantic по умолчанию проигнорирует его (если не настроить иначе). Это поведение важно для API, которые возвращают лишние поля.

## Сериализация: отправка данных в запросе

Pydantic умеет не только парсить JSON, но и превращать модель в словарь или JSON-строку. Это удобно для формирования тела запроса.

```python
new_user = User(id=0, name="Diana", email="diana@example.com")
payload = new_user.model_dump()          # dict/словарь
# или
json_payload = new_user.model_dump_json()  # JSON-строка
```

При отправке POST-запроса:

```python
response = client.post("/users", json=new_user.model_dump())
```

Если в модели есть поля со значениями по умолчанию (например, `is_active=True`), они тоже попадут в словарь. Можно исключить необязательные поля с помощью параметра `exclude_unset=True`.

## Кратко о дополнительных возможностях

Полезные функции:

- **Валидаторы** (`@field_validator`) — позволяют написать свою логику проверки для поля.
- **Конфигурация модели** — через внутренний класс `ConfigDict` можно задать, например, разрешить лишние поля (`extra = "ignore"`) или преобразовывать имена полей из camelCase в snake_case.
- **Alias** — если поле в JSON называется `userId`, а в модели мы хотим `user_id`, используем `alias_generator`.
- **Field** — дополнительная настройка атрибута модели. Позволяет задать ограничение кол-ва символов, диапазон значений, описание и многие другие параметры.

## Распространенные ошибки

1. **Забыли обновить модель после изменения API**.  
   Если в ответе появилось новое обязательное поле, Pydantic выбросит ошибку (`missing`). Это хорошо — вы сразу узнаете о несоответствии. Решение: добавить поле в модель или сделать его необязательным (`Optional[...]` или `... | None`).

2. **Несоответствие типов, которое Pydantic не может привести**.  
   Например, поле `int` получает строку `"abc"`. Pydantic попытается привести, но не сможет — будет ошибка. В тестах это сигнал, что сервер вернул данные не по спецификации/контракту.

3. **Использование `dict` вместо модели в коде**.  
   Новички часто парсят JSON в словарь и работают с ним, лишая себя всех преимуществ. Привыкайте сразу создавать модель после получения ответа.

4. **Необязательные поля с `| None` или `Optional`**.  
   Если поле может отсутствовать, обязательно указывайте `| None` или значение по умолчанию. Иначе Pydantic потребует его при создании модели, даже если в JSON его нет.

5. **Путаница с именами полей**.  
   В JSON ключи часто в camelCase (`userName`), а в Python принято snake_case (`user_name`). Используйте алиасы, чтобы не переименовывать все поля вручную.

## Краткий итог

- **Pydantic** превращает хаотичный JSON в строгие, предсказуемые объекты, обеспечивая валидацию данных на границе теста.
- Модели данных — это документированная спецификация того, что вы ожидаете от API. Они тесно связаны с аннотациями типов и делают код самодокументируемым.
- В автотестах Pydantic особенно полезен для:
  - парсинга ответов сервера;
  - формирования запросов;
  - раннего обнаружения изменений в API.
- Избегайте распространённых ошибок: всегда обрабатывайте ошибки валидации, правильно описывайте опциональные поля и следите за актуальностью моделей.

## Аналоги

- `dataclasses` (стандартная библиотека Python) - Лёгкий встроенный инструмент для создания классов-контейнеров. **Минусы**: не выполняет валидацию типов во время выполнения, нет встроенной сериализации и ограничений на поля. **Когда использовать**: для простых внутренних объектов, где не нужна строгая проверка данных.
- `attrs` - Более старая и гибкая библиотека, которая вдохновила создание `dataclasses`. Поддерживает валидаторы и конвертеры. **Минусы**: требует больше кода, чем `Pydantic`, нет нативной JSON-сериализации. **Когда использовать**: если нужны возможности, которых нет в стандартных `dataclasses`.
- `marshmallow` - Мощная библиотека для сериализации и десериализации. **Минусы**: схемы описываются отдельно от классов, что приводит к дублированию кода, медленнее `Pydantic v2`. **Когда использовать**: в проектах со сложными требованиями к сериализации, которые исторически используют `marshmallow`.

Г) Будет возбуждено исключение `TypeError`.

**4. Какое поведение по умолчанию у Pydantic при передаче дополнительных полей, не описанных в модели?**

А) Будет возбуждено исключение `ValidationError`.  
Б) Дополнительные поля будут добавлены в экземпляр модели.
В) Дополнительные поля будут проигнорированы (не вызовут ошибку).  
Г) Будет выведено предупреждение, но ошибки не будет.

**Правильный ответ:** В

В) Это модели, которые наследуются от нескольких родительских классов.
